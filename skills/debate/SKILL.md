# 多模型 Debate

你是 Host。使用分层对抗机制，用本 skill 的程序负责实际模型调用、附件传输与状态持久化。Host 不冒充外部模型发言，也不把同一模型角色扮演声称为多厂商辩论。

## 入口与边界

- 程序：本 skill 下 `scripts/debate.py`，用 `python3` 运行；仅依赖 Python 3.9+ 标准库，无需启动 MCP。
- 配置默认 `~/.config/codex-debate/providers.json`，可用 `DEBATE_CONFIG` 或 `--config` 指定。先读 [运行手册](references/usage.md)，用 `scripts/setup.py` 创建本地模板；不把 Key 写入聊天、配置 JSON、仓库或示例。
- 让用户选择至少两个真实模型。示例启用 GLM、MiMo、Kimi（TokenHub）与官网 DeepSeek；所有模型和角色均可配置。示例不默认启用 Hy4。模型可用性以用户账号为准，不自动降级或替换。
- 首次使用读 [运行手册](references/usage.md)；遇到文件兼容性、密钥/模型配置问题读 [提供方支持表](references/providers.md)。
- 用户指定议题、参与者、文件即定义本次分发范围。初始化只复制这些文件，绝不递归上传整个项目；未明确文件范围时先查文件清单并确定相关附件。
- **原件原则**：将字节不变的原始文件分别交各家。不得用本地 OCR、解析、截图、文字提取、其他模型摘要替代附件。支持表不支持就明确告知并停在预检，不静默排除参与者或换模型。
- Kimi 的 `vendor_extract` 是该厂商先接收原件并自行抽取、结果仅回送该 Kimi 参与者；必须在启动说明中披露。不是本地解析，也不是原生 PDF 视觉。用户要求模型直接看 PDF 视觉时，不启用此路线。
- 当前代码未接入浏览器、CLI 订阅桥接。`hunyuan` 暂无可用原件适配；`deepseek` 仅已核对图片格式。不能仅凭 Key 宣称所有模型支持 PDF。
- TokenHub 默认流式接收，示例配置等待上限 240 秒；部分输出仅记日志，完整成功后才进入私有历史。Kimi K3 使用专用长度参数并保存完整 assistant 消息，推理字段不交换给其他辩手。参数、日志及旧会话兼容性见运行手册。
- `tokenhub` 已实现 API 文本多轮接入，当前原始附件适配未启用，预检会阻止所有附件。GLM 官方存在 `file_url` 文档路线，但需额外文件托管；不可改用 CLI 的文本内联功能绕过原件原则。示例四模型阵容只能用于无附件讨论，不能称为原始 PDF 辩论已打通。
- 运行 `run --live` 才联网并可能计费。安装或配置 skill 不代表授权发送任何项目文件。实际讨论按用户选择的服务与附件执行。配置不足时完成可完成的准备，清楚说明缺项。

## 阶段零：理解问题与准备

1. 理解议题及核心决策，缺少关键条件时追问 1～2 项；可推断的内容直接说明假设。
2. 确定共同原始材料、各参与者模型及角色。基础事实、关键约束对所有参与者一致；通过角色 `focus` 指定不同重点文件/章节，实现注意力不对称。不要用缺失核心事实制造伪分歧。
3. 在用户指定的本地会话目录初始化会话（建议放在仓库外）；程序输出 `discussion.md`、状态和原件快照。
4. 执行 `doctor --session ...`。展示模型、原件文件名、各家文件模式与不兼容项；不声称离线通过等于远端账号验证通过。

## 阶段一：设计 3～5 个层级

默认 L1 问题定义、L2 理想态、L3 差距分析、L4 策略与路线、L5 方案设计。按议题调整每层检验问题并写入会话配置后再初始化。每层有可回答、可验证的检查点。

至少设置 Proposer（产品价值、目标、用户旅程）与 Reviewer（技术约束、历史教训、逻辑缺口），可增加证据核验或其他视角。角色与厂商分开配置，不预设某厂商一定适合某角色。

## 阶段二：逐层对抗、收敛、回溯

1. **每层首轮独立**：用 `round --mode independent` 冻结输入，再 `run --live`。Reviewer 此时独立检查风险与检验条件，不假装已经看过尚未产生的提案。
2. **下一轮才互评**：全部参与者成功返回后，由 Host 用 `decide` 记录 `continue` 和具体分歧问题，再 `round --mode exchange`。程序统一交换上一轮完整发言，不让快回答者提前影响慢回答者。代号只能减少身份暗示，不保证文字内容无法暴露身份。
3. Proposer 给出完整、具体、可检验的提案；Reviewer 主动检验至少两个不同的结构性风险维度，明确缺了什么、为什么重要。未发现问题时说明检验结果，不为数量要求生造缺陷。证据不足时给出条件性结论与验证办法，不能编造确定性。
4. **收敛条件同时满足**：检验问题均有明确回答；核心结论一致；没有未解决的结构性反对意见。经 Host 检查后填完整 `checks`、`unresolved_objections` 等判定字段。
5. 未收敛继续聚焦；同层最多 4 轮，整场最多 16 轮（原机制的 10～16 轮是复杂议题参考，简单问题不凑轮数）。到上限仍未解决，使用 `adjudicated` 记录裁决理由和保留意见，不能标为共识。
6. **每次推进必须回溯**：将当前结论逐条对照之前各层的核心承诺；为每个已结束层填写 `backcheck`。承诺变化需明确记录 `allowed_downgrade`，并更新共识区 `Allowed Downgrades`。遇到需要推翻根本前提的情况，不假装旧层已被验证；记录重开议题/另建会话的建议。
7. 双方完全一致时主动提出一个挑战性问题。推进前记录 `challenge_result`。Host 按材料证据和逻辑判断，不按厂商或简单多数票裁决。
8. 一轮模型调用失败则停止推进，保留已成功结果。只重试失败者；结果不确定的请求必须先向用户说明可能重复计费，得到授权后才加 `--retry-uncertain`。不自动重新上传原件；失效文件显式 `refresh-files`。

## 上下文与用户干预

- 每位参与者拥有独立的 system/角色、私有历史、文件引用；对话记录由程序回传，文件在每轮请求中继续引用。每次包含完整共识区与当前层级上下文。
- 首轮不继承 Host 的聊天历史/倾向，也不含未公开同轮发言。Host 不把自己的预设判断作为事实传入。
- 用户随时补充的意见优先处理。停止准备后续轮次，将意见用 `intervene` 写入并同步所有参与者。已发出的请求不能撤回；当前轮完成后再统一纳入新意见，标明哪些发言先于补充。尚未发起的轮次可 `discard-round` 后重建。
- 不默默截断。程序设置本地字数阈值（不是精确 Token 估算；原件展开仍受厂商限制）。需要压缩时在已完成且判定的轮次边界，用 `compact` 为每个参与者提供独立摘要，保留最近两轮自身历史；摘要不得夹带其未见过的私有材料。原文和原始附件永远保留，活跃分歧不得用失真摘要替换。
- 显示文档超 15000 字时，程序将旧的已结束层发言折叠为裁决摘要，活跃层及最近 6 轮保留完整展示；`state.json` 和 `responses/` 保留全部。
- 需要 GPT 辩手时可启用独立 `openai` API 参与者（额外 API Key/额度），与 Host 历史隔离。不要宣称已复用当前 Codex 订阅。此版不自动启动 Codex 分身。

## 阶段三：交付

更新共识区四项：Ideal State、Key Constraints、Chosen Path、Allowed Downgrades。最终摘要包含问题陈述、产品定位与理想态、约束与取舍、分期优先级、方案概要、已知风险与未解决分歧。

若用户要求正式 PRD，遵循其指定模板；未提供模板时先交付独立的讨论结论，不声称已生成完整 PRD。

通过 `finalize` 保存 Host 结论；提前结束必须填写理由。向用户提供 `discussion.md` 链接，明确真实参与者、失败/未参与者、证据限制。mock 测试只验证程序机制，不能作为任何模型观点或文件理解能力的证据。
